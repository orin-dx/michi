 Do we remove the pipeline from our setup then? Or do we change pipeline to make it available?

There's nothing to remove from Callisto, because it never depended on michi-pipeline. If you mean the Michi repo's crate, that's a product decision about Michi, not a Callisto setup question, so I'll answer it from Callisto's side. Tell me if you meant something else, such as the CI pipeline.

Why Callisto doesn't use it
- Wrong shape. Release execution is a synchronous plan run through a DAG (michi-graph), with each operation observing its provider and adopting or performing the effect (ADR 3). It needs no async runtime or stage runner.
- Licensing. callisto-model is MIT and must never depend on an FSL crate (invariant 2 in ARCHITECTURE.md). The other crates are FSL, so they could technically depend on it, but there's still no fit.
- The checkpoint work doesn't need it. The new version checkpoint is a git ref, not a pipeline.

Changing michi-pipeline to make it usable here would only be worth it if a Callisto need showed up that it could meet better than what we have. I haven't found one:
- Release execution is already built on michi-graph.
- External tools run through CommandRunner.
- Parallelism isn't a bottleneck. Reads are already batched or run side by side (just bench measures them).

Changing a crate to fit a consumer that doesn't need it adds maintenance on both sides. Callisto's explicit goal has been to stay lean.

Recommendation: leave Callisto as it is, and don't change michi-pipeline for Callisto's sake. Revisit if Callisto grows a real async or concurrent execution need, for example parallel publishes across registries with per-stage retry, and the same need shows up in Michi's other products.
