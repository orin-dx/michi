# Keep michi-pipeline small, record-centric, and replay-honest

The best-practice design for an in-process, embeddable Tokio step pipeline is a static DAG of steps with stable, caller-chosen string ids, validated in full before anything runs. It has one scheduler loop over a `JoinSet` with a concurrency cap, and it returns an immutable per-run record in which every step has exactly one terminal status and a reason. It resumes by skipping steps the record says definitively succeeded, under the same run id, so a `run_id:step_id` idempotency key stays stable for downstream deduplication. The proposed redesign already gets most of this right. `ExecStep` with ids and `depends_on`, a single `execute()` with a `Mode`, a caller-supplied `RunId`, `StepContext` with `idempotency_key() = run_id:step_id`, a returned `RunRecord`, reasoned statuses, and resume-from-record all match what Temporal, Step Functions, Dagster, Argo, Tekton, GitHub Actions and the provenance literature converge on. Where it falls short is at the edges. It has no status for a step that was cancelled or timed out mid-flight, which is ambiguous, not "skipped". It does not say what resume does with a step whose prior outcome was ambiguous. It does not bind resume to the same plan through a fingerprint. It keeps one circuit breaker for the whole pipeline. It has no per-step progress hook, so a crash mid-run loses the whole record. On build versus adopt, the honest result is that the world-class pieces michi needs are mostly already present (tokio `JoinSet`, `tokio::time`, michi-core's retry math). The one clear new adoption is tokio-util's `CancellationToken`. tower, petgraph, retry crates and breaker crates fail on fit, not quality, because michi's distinctive value is the replay-safety classification that those generic crates do not model.

Verification convention used below: claims with a source link were read in a primary source by the researchers unless marked **[unverified]**. That tag carries over the notes' [K], [prior] and "Unverified" labels for items that were cited from background knowledge and not re-fetched. Statements framed as recommendations, or prefixed "inference", are reasoning rather than sourced fact.

## Stable string ids, not handles or UUIDs, are the identity everyone converges on

Every orchestrator surveyed gives a step a caller-chosen identity that is unique within the definition and separate from its display name. GitHub Actions requires `job_id` to match `^[A-Za-z_][A-Za-z0-9_-]*` and treats `name` as display-only ([GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)). Argo keys nodes by ID with a separate `DisplayName` ([Argo workflow_types.go](https://raw.githubusercontent.com/argoproj/argo-workflows/main/pkg/apis/workflow/v1alpha1/workflow_types.go)). An Airflow task instance is "a specific run of that task for a given Dag" ([Airflow tasks](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html)). The libraries closest to michi's resume use case key memoization on **stable, user-chosen strings**. Inngest's `step.run(id, …)` id "is used to memoize step state across function versions" ([Inngest](https://www.inngest.com/docs/reference/functions/step-run)), and Prefect restores prior completed state on a cache-key match ([Prefect tasks](https://docs.prefect.io/v3/develop/write-tasks)). Bevy uses typed labels instead, so misspellings are compile errors ([bevy SystemSet](https://docs.rs/bevy/latest/bevy/ecs/schedule/trait.SystemSet.html)), but its systems are static code, and no measured evidence was found that typed handles reduce errors in pipeline libraries.

The proposed `ExecStep{id, name, …}` is therefore correct. Two refinements follow. First, wrap ids in `StepId`/`RunId` newtypes, per the Rust API Guidelines' C-NEWTYPE ("Newtypes provide static distinctions") ([API Guidelines](https://rust-lang.github.io/api-guidelines/checklist.html)). Second, validate a charset and length so ids stay short and copyable by agents. Anthropic reports that replacing arbitrary UUIDs with semantically meaningful identifiers "significantly improves Claude's precision in retrieval tasks by reducing hallucinations" ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)). One practitioner team found a UUID costs about 10 tokens and that "the more UUIDs in the prompt, the higher the error rate", though without measured rates ([Dexter](https://engineering.getdexter.co/2026/03/10/short-ids-for-llms/)). The same logic applies to `RunId`. If an agent has to echo it back to resume, a short semantic form beats a raw UUID. Better still, the host keeps the run implicit and maps "resume" to it.

The idempotency key format has direct precedent. Temporal recommends "a combination of the Workflow Run ID and the Activity ID as an idempotency key… consistent across retry attempts but unique among Workflow Executions", enforced "by the service you are calling… not by the Activity itself" ([Temporal](https://docs.temporal.io/activity-definition)). Beldi logs operations keyed by instance ID plus step number **[unverified]** ([Beldi](https://www.usenix.org/system/files/osdi20-zhang_haoran.pdf)). AWS's client tokens are reused across retries, and reusing a token with different parameters is a validation error ([AWS Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)). So `attempt` must stay out of the key, as the proposal has it. `attempt` stays in `StepContext` for logging and backoff only. One caution is inference: michi cannot deduplicate two starts that use the same `RunId`, so the docs should state what happens if a caller reuses one for a different plan or inputs. That is AWS's "same token, different parameters" hazard.

## The definition is a plan and the run record is the only thing that changes

All eight orchestrators surveyed separate an immutable definition from a per-run record, and none mutates the definition during a run. Examples are Step Functions' versioned machine versus execution ARN ([SFN redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)), Tekton's Pipeline versus PipelineRun ([Tekton](https://tekton.dev/docs/pipelines/pipelineruns/)), and Prefect's definitions versus run states ([Prefect states](https://docs.prefect.io/v3/concepts/states)). W3C PROV draws the same line. A _Plan_ is "a set of actions or steps intended by one or more agents to achieve some goals", and an _Activity_ is "something that occurs over a period of time" ([PROV-DM](https://www.w3.org/TR/prov-dm/)). Provenance research calls these prospective and retrospective provenance ([Ragan et al.](https://faculty.cc.gatech.edu/~aendert3/resources/ragan-vast-2015.pdf)). The proposal's move from a mutated reusable definition to a returned `RunRecord` is the single most important correction in the redesign.

The record should be a plain value, serializable under the existing `serde` feature, with persistence left to the caller (inference). Its minimum contents, drawn from the industry survey, are: `run_id`; per step a terminal status with a reason, the attempt count with per-attempt classification, timing, and the error; a derived overall outcome; and a **plan fingerprint** over `(id, depends_on)`. The fingerprint is what lets resume reject a drifted plan. Step Functions requires that you "must start a new execution if you update your state machine definition" ([SFN redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)). Dagster requires re-executed step keys to be consistent with the parent plan ([Dagster execution API](https://docs.dagster.io/_modules/dagster/_core/execution/api)). Nextflow invalidates its cache when hashed inputs change ([Nextflow](https://docs.seqera.io/nextflow/cache-and-resume)). Closures cannot be hashed, so structure is the practical stand-in (inference). Keep `RunRecord` fields private behind accessors (C-STRUCT-PRIVATE) and mark it `#[must_use]`.

Data passing deserves a deliberate non-decision. Dataflow systems pass outputs, and once resume exists that forces serialization. Inngest JSON-serializes every return value, so a `Date` comes back as a string ([Inngest](https://www.inngest.com/docs/reference/functions/step-run)). Dagster's resume-from-failure "requires an I/O manager that can access outputs from other runs" ([Dagster run retries](https://docs.dagster.io/deployment/run-retries)). Concurrency utilities like errgroup carry no outputs ([errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup)). For michi, side-effect-only steps (`Result<(), …>`) with state shared through `Arc` captures is the right default. If anything flows into the record, it should be a small optional summary for agent display, not an input to downstream steps (inference).

## A status model built around recovery verbs, not lifecycle phases

Production status models are large because they cover distributed lifecycles: Airflow has fourteen task states and Prefect twenty ([Prefect states](https://docs.prefect.io/v3/concepts/states)). Most of those (scheduled, queued, deferred, late, removed) mean nothing in-process. Three distinctions recur that do matter. First, **skips must never let a run read as succeeded**. Tekton reports `Completed` rather than `Succeeded` when "one or more Tasks were skipped" ([Tekton](https://tekton.dev/docs/pipelines/pipelineruns/)), and GitHub Actions' skipped-as-success behaviour lets required checks pass despite upstream failure ([Jake Wharton](https://jakewharton.com/fan-in-to-a-single-required-github-action/), [actions/runner#491](https://github.com/actions/runner/issues/491)). Second, **harness failure is distinct from step failure**. Argo separates `Failed` ("non-zero code") from `Error` ("error other than a non-zero exit code") ([Argo types](https://raw.githubusercontent.com/argoproj/argo-workflows/main/pkg/apis/workflow/v1alpha1/workflow_types.go)), and Prefect separates `Crashed` from `Failed` ([Prefect states](https://docs.prefect.io/v3/concepts/states)). Third, **timeouts are a distinct outcome**, as in GitHub's `timed_out` conclusion ([GitHub check runs](https://docs.github.com/en/rest/checks/runs)) and Temporal's per-type timeouts ([Temporal failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).

The proposed reasons all have analogues except one. `Skipped(PrerequisiteFailed)` matches Airflow `upstream_failed` and Argo `Omitted`. `Skipped(Cancelled)` matches GitHub and Tekton cancellation. `CompletedEarlier` matches Prefect `Cached` and Step Functions redrive keeping successes. `NotRun(CircuitOpen)` has no direct analogue, but it is correct. An open breaker fails fast without calling the operation **[unverified]** ([Fowler](https://martinfowler.com/bliki/CircuitBreaker.html)), so nothing ran, the step is safe to run on resume, and it should not count as a failed attempt.

The gap is the mid-flight case. A step that was running when the run was cancelled, or when its timeout dropped its future, may have performed its effect. Under RFC 9110 that is exactly a "communication failure … before the client is able to read the server's response" ([RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)). It belongs with ambiguous outcomes, not with `Skipped(Cancelled)`, which should mean "cancelled before start". The redesign should add an explicit `Failed(Ambiguous{cause: Timeout | Cancelled | Transport})` (or `OutcomeUnknown`) terminal status. Two more additions round out the model: a `Panicked` or harness-error reason distinct from a step's own error, and an overall verdict that cannot be `Succeeded` when any step is skipped, not run or ambiguous (inference built on the sources above). Following conc's observation that errors after cancellation are mostly noise ([conc pool](https://pkg.go.dev/github.com/sourcegraph/conc/pool)), the record should separate the **root-cause** failure from consequential skips. Then an agent sees one cause, not N errors. Each reason should map one-to-one to a recovery verb an agent can act on: retry, verify then resume, fix input, or no action. That is Anthropic's "specific and actionable" guidance applied to statuses ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)). Mark `StepStatus` and every reason enum `#[non_exhaustive]`.

## Resume is forward recovery, at least once per step, and must respect ambiguity

michi's four-way replay classification is a near-literal implementation of RFC 9110 §9.2.2. Idempotent requests "can be repeated automatically if a communication failure occurs". A client "SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent … or some means to detect that the original request was never applied" ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)). Not-executed is the "never applied" case. Ambiguous (timeout, 502, 504) is the communication-failure case. One caveat is inference: treating 429 and 503 as "not applied" is a widespread convention, not an RFC guarantee. §15.6.4 defines 503 only as temporary overload ([RFC 9110 §15.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6)), and an intermediary's 503 could mask partial application, so the docs should state the assumption and let steps override it. Gating ambiguous retries on idempotency is **stricter than every orchestrator surveyed** (inference). Temporal says activities "may be executed more than once… may even partially complete more than once" and retries anyway, leaving idempotency to the author ([Temporal](https://docs.temporal.io/activity-definition)). Airflow tells authors to replace INSERT with UPSERT ([Airflow best practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html)). michi's rule is a genuine differentiator for agent tools and should be kept.

Resume in the proposal is what the build-systems literature calls a **dirty-bit rebuilder**, where dirty means "not definitively succeeded in record R". The scheduler and the rebuilder are independent axes: "a 'scheduler'" can be "cleanly separated from" the part that decides "whether a key needs to be rebuilt" ([Build Systems à la Carte](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems.pdf)). It is not input-sensitive. A step whose inputs changed between runs would be wrongly skipped, and input-sensitive skipping needs verifying traces and determinism, which belong to build systems, not michi. The docs should say plainly that resume continues an interrupted run and is not incremental recomputation. It is also saga-style forward recovery from save-points ([Sagas](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)), with each completed step serving as a save-point.

Durable-execution research sets the ceiling. Durable Functions proves observably exactly-once execution only because "the storage system [provides] an atomic commit mechanism", and even then "external calls can be duplicated if there are multiple attempts at executing a work item" ([Durable Functions](https://www.microsoft.com/en-us/research/uploads/prod/2021/10/DF-Semantics-Final.pdf)). michi has no atomic commit between "the effect happened" and "the record says so". Resume is therefore **at least once per step**, and effects are exactly-once only when the step passes `idempotency_key()` to a deduplicating downstream. That is the end-to-end argument **[unverified]** ([Saltzer, Reed & Clark](https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf)). Never claim exactly-once. There is an advantage over Temporal and Durable Functions here: the orchestration is the static DAG, deterministic by construction, so users carry no replay-determinism burden (inference).

Four resume rules follow, and the proposal states none of them. **Keep the same `RunId`**, as Step Functions redrive (same ARN), GitHub re-runs (same SHA and ref) and the key's stability all require ([SFN redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html), [GitHub re-runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)). A fresh id defeats downstream deduplication. **Reject plan drift** with the fingerprint. **Treat a prior ambiguous step as ambiguous again**: re-invoke it only if it is idempotent, otherwise surface it for reconciliation, because treating ambiguous as not-done turns resume back into blind replay. **Never implicitly re-run completed steps.** Step Functions' rerun of successful branches on `States.DataLimitExceeded` is a documented pitfall ([SFN redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)). To survive a process crash rather than just returned errors, callers need to persist progress incrementally. A per-step-completion observer callback is the minimal embeddable affordance for that (inference).

Retry policy should follow the cross-source consensus. Use bounded attempts with randomized exponential backoff, and retry at **one layer only**: 3 retries across 5 layers is about 243x load ([AWS](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)), and the SRE book warns against "issuing retries at multiple levels" ([SRE ch. 22](https://sre.google/sre-book/addressing-cascading-failures/)). Budget retries too. The SRE book allows retries only while the retry ratio is "below 10%", which holds load growth to about 1.1x versus "just below 3X" with per-request caps alone ([SRE ch. 21](https://sre.google/sre-book/handling-overload/)). tower's `TpsBudget` implements the same idea, warning "It's generally dangerous to implement retries without some limiting factor" ([tower budget](https://docs.rs/tower/latest/tower/retry/budget/index.html)). Temporal recommends bounding retries by a total Schedule-To-Close timeout rather than attempts ([Temporal retry policies](https://docs.temporal.io/encyclopedia/retry-policies)), which argues for both a per-attempt timeout and a total step budget. Compensation fits only definitive failures after earlier effects commit, and the Sagas paper admits a failing compensation leaves "the system … stuck" ([Sagas](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)). A saga coordinator is out of scope. Listing definitively succeeded steps in completion order in the record lets callers compensate themselves.

## One scheduler loop, a slot cap, cooperative cancellation, and negligible overhead

Every task-graph system surveyed runs the same loop. It keeps a remaining-dependency count per node, pushes newly ready dependents into a queue, and pops while a slot is free. Cargo's job queue "must not spawn more than N threads of work" and calls its own prioritization "relatively rudimentary" ([Cargo job_queue](https://github.com/rust-lang/cargo/blob/master/src/compiler/job_queue/mod.rs)). Its std-only `DependencyQueue` (remaining-deps map, reverse-deps map, priority) is the best design reference ([dependency_queue.rs](https://github.com/rust-lang/cargo/blob/master/src/util/dependency_queue.rs)). Kahn's ready-queue algorithm is O(V+E) and detects cycles **[unverified]** ([Kahn 1962](https://doi.org/10.1145/368996.369025)). Any greedy list schedule is within (2 − 1/m) of optimal makespan **[unverified]** ([Graham 1969](https://doi.org/10.1137/0117039)), and critical-path heuristics need durations michi does not have **[unverified]** ([Kwok & Ahmad](https://doi.org/10.1145/344588.344618)). A FIFO ready queue with ties broken by declaration order is therefore sufficient, and it makes records reproducible. Because `depends_on` is static, this topological scheduler is the right one. Dynamic dependencies would need a restarting or suspending scheduler ([Build Systems à la Carte](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems.pdf)) and should be an explicit non-goal.

The proposal's single `execute()` with `Mode` is right. Inference: implement `Sequential` as the same loop with a cap of one and deterministic declaration-order dispatch. That removes the divergence between today's two executors, and it satisfies the industry note's point that sequential mode needs deterministic ordering, not merely a cap of one. Use `Parallel{max_concurrency: NonZeroUsize}`, since errgroup documents the `SetLimit(0)` hazard that a zero cap creates ([errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup)). The cap belongs in the dispatch loop (`while in_flight < max`), not in a `Semaphore` inside spawned tasks, which would park spawned tasks and admit them in wake order (inference). Current michi already uses `JoinSet` with no cap. `JoinSet` is the right primitive: it aborts all tasks on drop, surfaces a panic as `JoinError`, and `join_next` is cancel-safe ([JoinSet](https://docs.rs/tokio/latest/tokio/task/struct.JoinSet.html)). So no step outlives `execute()`, and a panicking step becomes a step failure rather than unwinding the executor. `FuturesUnordered`/`buffer_unordered` lose panic isolation and want a stream known up front **[unverified]**.

Failure policy needs a name. Turborepo offers `--continue=never` (cancel all), `dependencies-successful` (cancel only dependents) and `always` ([Turborepo](https://turborepo.dev/docs/reference/run)). Cargo's fail-fast stops scheduling and then waits "for pending work to finish" ([Cargo](https://github.com/rust-lang/cargo/blob/master/src/compiler/job_queue/mod.rs)). Structured concurrency defaults to cancelling siblings on failure ([N. J. Smith](https://vorpus.org/blog/notes-on-structured-concurrency-or-go-statement-considered-harmful/)), but JEP 505 makes the policy pluggable, including an `awaitAll` that "simply waits for all subtasks to complete" ([JEP 505](https://openjdk.org/jeps/505)). For a DAG, the right default is to continue independent branches and skip transitive dependents. `FailFast` is opt-in (inference). Fail-fast should cancel the run token, drain until a grace deadline, and then `abort_all`, recording unstarted steps as `Skipped(Cancelled)` and in-flight ones as ambiguous. Backoff sleeps should `select!` on cancellation. Following SRE deadline propagation ([SRE ch. 22](https://sre.google/sre-book/addressing-cascading-failures/)), `StepContext` should carry the run's child cancellation token and remaining deadline.

Circuit breaker scope is the main performance-and-correctness defect in the current design. One breaker shared by all steps lets one failing dependency trip unrelated steps. Envoy keeps failure counters per upstream host ([Envoy FAQ](https://www.envoyproxy.io/docs/envoy/v1.9.0/faq/transient_failures)), and resilience4j/Polly name instances per downstream **[unverified]**. Use a breaker registry keyed by an optional step-declared `breaker_key`, long-lived across runs because a single run produces few samples (inference). Overhead is not a concern: tokio task overhead measured informally is "at most 50ns" ([alamb](https://github.com/alamb/rust_tokio_overhead)), so 500 steps cost well under a millisecond against millisecond-to-second step latencies (inference). The real performance risks are uncapped fan-out, retry amplification and idle slots, and the cap, the budget and the keyed breaker address all three. `max_concurrency` doubles as a bulkhead.

## Ease of use comes from one validation pass, closures, and paused-clock tests

Of the libraries examined, the common shape separates what a step does (closure or trait), how it is retried (a policy value), and when it runs (dependency declaration) ([tower](https://docs.rs/tower/latest/tower/), [Temporal](https://docs.temporal.io/encyclopedia/retry-policies), [Prefect](https://docs.prefect.io/v3/develop/write-tasks)). `ExecStep{runner}` plus options fits this. Temporal and Prefect both configure retries per activity, so a per-step retry override should be available. Validation is where today's michi is weakest. `depends_on(&str, &str)` returns `()` and defers unknown ids and cycles to execute time (local source, `crates/michi-pipeline/src/lib.rs`). dagrs returns `Result<Graph, DagrsError>` at build time ([dagrs](https://docs.rs/dagrs/latest/dagrs/)). michi should run one pass that rejects unknown dependencies, duplicates, self-dependencies and cycles, and returns **all** violations, not just the first. An invalid plan must come back as `Result::Err` before execution, so it cannot be confused with a run that happened and failed. Exposing that pass as `plan(&steps, &opts) -> Result<Plan, PlanError>` gives agents a cheap dry-run preview and makes validation testable on its own (inference). For MCP, step failures go in an `isError: true` tool result, not a protocol error, with structured content duplicated as text ([MCP tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). Default rendering should be concise: non-completed steps plus a `completed: 7/10` count, with a detailed mode available, following Anthropic's response-format pattern.

Two small API-guideline points apply. C-CUSTOM-TYPE argues against meaning-carrying bools, so `is_idempotent() -> bool` reads better as `fn replay(&self) -> Replay { Unsafe, Idempotent }` ([API Guidelines](https://rust-lang.github.io/api-guidelines/checklist.html)). Resume should be a separate `resume(&RunRecord, …)` entry point, or an explicit options field, not a positional `Option<&RunRecord>`. Testability comes nearly free. `#[tokio::test(start_paused = true)]` auto-advances the clock "to the next pending timer" when idle ([tokio pause](https://docs.rs/tokio/latest/tokio/time/fn.pause.html)), making backoff, timeouts and breaker windows instant, as long as michi uses `tokio::time` throughout and jitter stays injectable through the existing seed. The cap is tested with an in-flight high-water mark, fail-fast by asserting virtual elapsed time, and resume by running, editing the record, and resuming. That last test needs `RunRecord` to be a value type with public read accessors. loom, turmoil and madsim add little here (inference).

## Adopt the runtime, build the replay-safety layer

The maintainer's principle holds up, but applied honestly it adds only one dependency. tokio is already the world-class core, and the components michi builds encode replay safety that no generic crate models. | Steps as tower `Service`s | tower 0.5.3 | **Avoid** | `poll_ready`, `&mut self`, `Clone`/`Buffer`, `clone_request` and boxed errors are heavy ceremony that would erase the typed `ExecutionError`/`ReplayClass` (inference). tower is fine inside a step's own HTTP client, but then michi must not also retry |
| Compensation / saga coordinator | none | **Avoid** (non-goal) | It needs a durable log and compensations that cannot fail ([Sagas](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)) |
| Persistence / durable store | none | **Avoid** (caller's job) | The record is a serde value; an observer hook enables incremental persistence |

## The redesign's divergences cluster at the edges, not the core

Inside an embeddable library the line against orchestrator creep is clear. Per-run concurrency transfers. Airflow pools, GitHub concurrency groups and Argo semaphores are cross-run and need a server, and even Dagster's concurrency limits are "only applied on a per-run basis" ([Dagster](https://dagster.io/docs/guides/build/jobs/job-execution)). Scheduling, persistence servers, UIs, event-history replay, cross-process workers, dynamic dependencies, trigger-rule languages, compensation, input-hash memoization and critical-path priorities all belong to orchestrators or build systems. Each would trade michi's main selling point, being a small library that renders agent-legible results, for features its users get elsewhere. The opinionated layer worth building is narrow: the replay classification, the reasoned status model, idempotency keys, resume semantics, and agent-facing rendering.

Measured against that, the proposal diverges from best practice in seven places. It conflates mid-flight cancellation with not-started cancellation and has no ambiguous terminal status. It leaves resume's treatment of prior ambiguous steps undefined. It has no plan fingerprint and does not state that resume must reuse the `RunId`. It keeps a single pipeline-wide breaker. It has no retry budget and no total per-step time budget. It has no per-step completion hook, so the record is lost on crash. It does not specify an all-violations validation pass that is separate from execution results, or the failure policy for independent branches. The remaining items are hygiene: an overall verdict that is never `Succeeded` with skips, a harness-versus-step failure split, `NonZeroUsize`, `#[non_exhaustive]`, newtyped ids, and an enum in place of the idempotency bool.

## Conclusion

The research shifts the framing of the redesign. The hard problem is not scheduling, which is solved, cheap and well served by tokio. It is being honest about what a step's outcome means once processes, timeouts and cancellation intervene. michi's RFC 9110-grounded refusal to auto-retry ambiguous non-idempotent work is stricter than Temporal, Airflow or Step Functions, and that strictness is the product. The redesign should extend it consistently to cancellation, timeouts and resume rather than letting those paths quietly reintroduce blind replay. Build-versus-adopt confirms the principle in an unexpected way: "adopt world-class pieces" mostly means trusting the tokio michi already uses, adding tokio-util, and resisting tower and petgraph whose abstractions would dissolve the typed replay model.

Ranked changes to the proposed redesign:

1. Add an ambiguous terminal status (`Failed(Ambiguous{Timeout | Cancelled | Transport})`). Restrict `Skipped(Cancelled)` to steps never started. Record in-flight cancellation and timeout of non-idempotent steps as ambiguous.
2. Define resume semantics explicitly. It reuses the prior `RunId`, rejects a mismatched plan fingerprint over `(id, depends_on)`, re-invokes prior ambiguous steps only if idempotent (otherwise it surfaces them), never re-runs `CompletedEarlier` steps, and is documented as at-least-once, not incremental recomputation.
3. Replace the pipeline-wide breaker with a registry keyed by an optional per-step `breaker_key`, reusable across runs, and add a run-scoped retry budget in michi-core plus a per-step total time budget.
4. Validate the whole plan before running (unknown, duplicate and self dependencies, cycles), return all violations as `Err(PlanError)` separate from `RunRecord`, and expose it as a dry-run `plan()`.
5. Implement one scheduler loop on `JoinSet` with `Parallel{max_concurrency: NonZeroUsize}`, `Sequential` as cap 1 with declaration-order dispatch, and a named `FailurePolicy` defaulting to continue-independent with opt-in `FailFast` (cancel, drain to grace, `abort_all`).
6. Adopt tokio-util `CancellationToken` behind michi's newtype, and put a child token and remaining deadline on `StepContext`.
7. Add a per-step completion observer so callers can persist the record incrementally and survive crashes.
8. Make the overall verdict never read `Succeeded` with skipped, not-run or ambiguous steps. Separate harness failures (panic) from step errors, and the root cause from consequential skips.
9. Apply type hygiene: `StepId`/`RunId` newtypes with a short-slug charset, `#[non_exhaustive]` status and reason enums, a `Replay` enum in place of `is_idempotent() -> bool`, a separate `resume()` entry point, and a `#[must_use]` `RunRecord` with private fields and serde behind the feature.
