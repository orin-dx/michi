# michi-pipeline

## 0.6.0

- michi-pipeline: `RunRecord::needs_verification()` and `StepRecord::awaits_verification()` no longer list idempotent steps, which resume re-runs anyway. Each `StepRecord` now records its step's `Replay` (`StepRecord::replay()`), set by the executor and by `RunRecord::from_parts` from the plan; a record without it (saved by hand or by an older version) still counts as not idempotent. Prechecked steps stay listed, since their precheck may not be able to tell and a caller's verdict takes precedence. With `serde`, the record serializes `replay` when known and reads records without it.
- michi-pipeline: blocking steps. `step_blocking(|ctx| -> Result<(), ExecutionError>)` (with `.idempotent()`, like `step_fn`) runs each attempt on Tokio's blocking thread pool, for steps that shell out to CLIs. A blocking closure keeps running after the executor stops waiting (a timeout, cancellation, a dropped run), so the closure's `ctx.cancellation()` fires at that point too, and the abandoned attempt's effect is unknown. A non-idempotent blocking step never starts a second closure while an earlier one with the same idempotency key is still running in the process: such an attempt fails with an unknown effect without calling the closure.
- michi-pipeline: per-key concurrency limits. `ExecStep::concurrency_key(key)` puts a step in a key (one per step), and `ExecOptions::concurrency_limit(key, NonZeroUsize)` caps how many steps of that key run at once, within the mode's overall cap. A step whose key is full waits without holding back other steps, and freed slots go to the earliest-declared step that can run, so dispatch stays deterministic. Keys without a limit are unlimited.
- michi-pipeline: deadline groups. `ExecStep::deadline_group(key)` with `ExecOptions::group_deadline(key, window)` gives several steps one shared window that opens when the group's first step is dispatched, so steps started at different times expire together. A step's deadline is the earlier of its own and its group's. A step that would start after its group's window closed is not run: it ends `Failed` with the new `ExecutionError::DeadlinePassed` (not retryable, not applied), and resume runs it again in a new window.
- michi-pipeline: poll steps. `poll_step(schedule, check)` calls an async check on a fixed `PollSchedule` (default: at once, then after 2 s, 4 s, 8 s, 16 s, then every 30 s) until it answers `Readiness::Ready`, returns a non-retryable error, or the step's deadline (its own or its deadline group's) or cancellation stops it. The whole poll is one attempt: it never draws from the retry budget, it runs until its deadline rather than the attempt timeout (which bounds each check instead), and when time runs out it fails with `ExecutionError::DeadlinePassed` naming the last observation. Supporting additions: `Step::attempt_bound()` returning `AttemptBound::{Timeout, Deadline}`, `StepContext::attempt_deadline()` and `StepContext::attempt_timeout()`.

## 0.5.0

- michi-pipeline: retries and resume no longer repeat an effect that may already have landed.
  
  - **Breaking:** `ExecutionError::Failed` has a third field, `effect: Effect` (`NotApplied` or `Unknown`). Build it with the new constructors: `failed(msg)` (not retryable, effect unknown, the default), `refused(msg)` (not retryable, not applied), `rejected(msg)` (retryable, not applied) or `transient(msg)` (retryable, effect unknown). `ExecutionError::effect()` reports the effect of any error.
  - **Breaking:** a non-idempotent step that fails with an unknown effect (`failed(msg)`, an HTTP 500 or other 5xx) now ends `OutcomeUnknown(StepFailed)`, not `Failed`, and resume holds it until verified. Before, resume ran it again and could commit twice. Use `refused(msg)` for failures that certainly had no effect.
  - **Breaking:** `ReplayClass::Definitive` is replaced by `Refused` (not applied) and `Ambiguous` (effect unknown).
  - **Breaking:** `ExecutionError::refused` counts as healthy for the circuit breaker (like an HTTP 4xx), so validation failures no longer open it. `PlanFingerprint` parses only 16 lowercase hex digits (it used to accept a leading `+` and uppercase).
  - Precheck: a `Replay::Prechecked` step implements `Step::precheck`, which runs before every attempt and answers `Precheck::Applied` (the step ends `CompletedEarlier` without running), `NotApplied` (it runs) or `Unknown` (it doesn't; `NotRun(Unverified)` if nothing ran yet). Resume uses it instead of a manual verdict.
  - Durable starts: `ExecOptions::durable_starts(observer)` takes a `DurableObserver`, and a step runs only after its `record_start` saves the in-flight marker; if that fails or panics, the step ends `NotRun(StartNotRecorded)` without being invoked. This closes the gap where a crash rebuilt a step that ran as `Pending`.
  - Records saved by 0.4 still load: a `Failed` error without `effect` reads as `Unknown`, and the attempt class `definitive` reads as `Ambiguous`, so resume holds such steps instead of re-running them.
  
  michi-core: `UnknownCause::StepFailed` (rendered `step_failed`) and `NotRunReason::{Unverified, StartNotRecorded}` (rendered `unverified`, `start_not_recorded`), on enums that were already `#[non_exhaustive]`. `@orin-dx/michi`'s `renderPipeline` accepts the three new reasons.
- michi-pipeline: `Plan` validation and ordering now come from `michi-graph`. Execution order, the fingerprint and every `PlanViolation` are unchanged, with two exceptions: a step that can never run because it sits between two cycles (depending on one, depended on by another) is no longer listed in `PlanViolation::Cycle`, which now lists exactly the steps on a cycle; and `PlanViolation` gains `TooManySteps` for plans over `u32::MAX - 1` steps (it is `#[non_exhaustive]`, so existing matches keep compiling).

## 0.4.0

- michi-pipeline: public types can now grow in 0.4.x without breaking callers.
  
  - **Breaking:** the re-exported `RetryConfigError` is `#[non_exhaustive]`, so a `match` on it needs a `_` arm.
  - **Breaking:** `RunRecord::to_pipeline()` returns michi-core's `Pipeline`, whose `Pipeline` and `PipelineStep` are now `#[non_exhaustive]`: read their fields as before, but build them with `Pipeline::new` and `PipelineStep::new`.
  - `FnStep` implements `Debug` (showing its replay class) without requiring the closure to be `Debug`. The re-exported `RetryConfig` implements `PartialEq`.
  - `RunRecord` accessors (`outcome()`, `steps()`, `step()`, `error()`, `render()`, …) are `#[must_use]`, so discarding their result now warns.
- Packaging and docs: the minimum supported Rust version is now 1.93 (was 1.96). The crates and npm packages ship their license text, michi-pipeline ships a README, docs.rs builds michi-core with the `serde`, `schemars` and `miette` features, the READMEs' links work on crates.io and npm, and michi-pipeline re-exports `RetryConfig`, `RetryConfigError`, `RetryBudget` and `IdempotencyKey`, so configuring retries needs no direct michi-core dependency.
- michi-pipeline: run records no longer misreport a run, and retries follow the server and spread out.
  
  - **Breaking:** `RunRecord::from_parts(run_id, saved_fingerprint, &plan, steps)` now takes the plan and returns `Result<RunRecord, ResumeError>`. It refuses a fingerprint that is not the plan's (`FingerprintMismatch`) and a saved step the plan lacks (`UnknownStep`), lists a plan step with no saved record as `Pending`, and keeps the **last** record saved for a step, so the documented observer pattern (`StepRecord::in_flight` on start, the finished record on finish) rebuilds a finished step as finished instead of in flight.
  - **Breaking (serde):** a serialized `RunRecord` carries `plan_steps`, and deserializing fails if `steps` does not list that many distinct steps. A record missing steps used to read as `Succeeded`. Records saved by 0.3 need `"plan_steps": <number of plan steps>` added.
  - `RunRecord::outcome()` is `Succeeded` only when every plan step is listed and succeeded. A step a rebuilt record shows as `Running` makes the outcome `OutcomeUnknown` and is a root cause.
  - `RunRecord::needs_verification()` lists every step resume holds for verification: `OutcomeUnknown`, `Panicked` and `Running` (it listed only `OutcomeUnknown`). New `StepRecord::awaits_verification()`.
  - `RunRecord::error()` is `None` only for a successful run: with no root cause it names the first step that did not succeed (a cancelled run, a pending step).
  - A step that returns `ExecutionError::Cancelled` while the run was not cancelled now ends `Failed` (a root cause; dependents name it in `caused_by`) instead of `Skipped(Cancelled)`. Resume runs it again.
  - A server's `retry_after` (HTTP 429/503 or `CircuitOpen`, also inside `StepFailed`) is waited in full even past `RetryConfig::max_delay`, which used to cut a 120 s hint to 30 s. If the wait would pass the step deadline, the step stops retrying at once (`step deadline reached`).
  - Retries get per-retry jitter by default, derived from the run id, step id and attempt, so steps that fail together no longer retry in lockstep and a run's delays stay reproducible. `ExecOptions::jitter_seed(x)` still fixes one seed for everything.
  - HTTP 4xx responses other than 408 and 429 no longer count as circuit-breaker failures (the downstream answered); they reset the failure count like a success. A caller's bad requests can no longer open the breaker for a whole key.
  - `ExecOptions::step_deadline(Duration::MAX)` or a huge `ExecStep::deadline` means no deadline instead of panicking the step with "overflow when adding duration to instant".
  - `RunId::unique` ids are `{prefix}-{millis}-{pid}-{counter}`: the new separator stops two processes from printing the same id (pid 1388 with counter 1152 and pid 50000 with counter 0 both printed `…-12kw0`).

## 0.3.0

The removed or changed APIs named below (`execute_pipeline`, `execute_pipeline_parallel`, `StepDependencies`, `CircuitBreaker::call` and the old error variants) describe pre-release history: they never shipped in a published version, so nothing published needs migrating.

- **Breaking:** the execution API is redesigned (see `docs/spec/08-pipeline-execution.md`). `execute_pipeline`, `execute_pipeline_parallel`, `StepDependencies`, positional runner lists, `CircuitBreaker::call`/`CircuitBreaker::new(retry, timeout, threshold, open)` and the `StepCountMismatch`, `UnknownStepId`, `DuplicateStepId` and `CyclicDependency` error variants are removed. In their place:
  - `StepId` and `RunId` are validated slugs (1 to 64 ASCII letters, digits, `_`, `-`, `.`). `RunId::unique(prefix)` builds one without a UUID dependency.
  - `ExecStep` defines a step (id, display name, `depends_on`, runner, optional retry, attempt timeout, deadline and breaker key). `Plan::new` validates every step up front and returns all violations at once as `PlanError` (duplicate ids, unknown and self dependencies, cycles). `Plan::execution_order()` is the dry run; `Plan::fingerprint()` hashes ids and dependencies.
  - `execute(&plan, run_id, &opts)` returns a `#[must_use]` `RunRecord` instead of mutating a `Pipeline`: per-step status, reason, error, attempts with their replay class, timing and root cause; `outcome()` is `Succeeded` only if every step completed; `root_causes()`, `consequential()`, `needs_verification()`, `completion_order()`, `error()`, `to_pipeline()` and `render()`.
  - `resume(&record, &plan, &ResumeOptions)` continues a run under the same run id: completed steps become `CompletedEarlier` and are not re-run, a changed plan is refused (`ResumeError`), and steps whose outcome is unknown are re-run only if idempotent or verified by the caller (`Verification::Applied` / `NotApplied`).
  - `ExecOptions`: `Mode::Sequential` (default) or `Mode::Parallel { max_concurrency }`, `FailurePolicy::SkipDependents` (default) or `FailFast`, retry policy, per-attempt timeout (default 30 s), per-step deadline, jitter seed, cancellation token and grace period (default 5 s), retry budget, breaker registry and observer.
- **Breaking:** `Step::run` takes a `&StepContext` (run id, step id, attempt, child cancellation token, deadline, `idempotency_key()` = `run_id:step_id`) instead of the attempt number, and `Step::is_idempotent() -> bool` is replaced by `Step::replay() -> Replay` (`NotIdempotent` by default, or `Idempotent`). `step_fn` closures receive an owned `StepContext`.
- **Breaking:** with the default `SkipDependents` policy, a failure skips only the failed step's transitive dependents; independent steps keep running, also in sequential mode. Before, sequential execution stopped at the first failure. `FailurePolicy::FailFast` restores stop-on-failure.
- **Breaking:** a non-idempotent step whose last attempt timed out, got HTTP 502/504 or was dropped after cancellation ends `OutcomeUnknown` and is never replayed automatically, by retry or by resume. A step dropped mid-flight is no longer reported as skipped.
- **Breaking:** cancellation now drops a running attempt once the grace period has passed, recording it as ambiguous; before, an in-flight step always ran to completion. Backoff sleeps end as soon as the run is cancelled.
- **Breaking:** a panicking step ends `Panicked` and the run continues; before, `execute_pipeline_parallel` resumed the panic in the caller.
- **Breaking:** `CancellationToken` wraps tokio-util's token: it is awaitable (`cancelled()`) and has `child_token()`. New dependency: `tokio-util` 0.7 (not exposed in the public API).
- Circuit breakers are keyed: a `BreakerRegistry` holds one breaker per key (the step's `breaker_key`, defaulting to its id), shareable across runs. Each keeps the mutex-and-generation state machine; a step is admitted once and reports one outcome, a half-open probe gets one attempt, an open breaker ends the step `NotRun(CircuitOpen)` without invoking it, and cancellation is not counted as a failure.
- Retries are limited per run by `michi_core::resilience::RetryBudget` (10% of successes, reserve 10, cap 100 by default; `ExecOptions::no_retry_budget()` turns it off) and by an optional total step deadline.
- New `StepObserver` (or any `Fn(&RunId, &StepRecord)`): called synchronously as steps start and finish, so callers can persist progress; `StepRecord::in_flight` and `RunRecord::from_parts` rebuild a run after a crash, and resume treats a step left `Running` as possibly applied.
- A panic in a `StepObserver` is caught: the run continues, the observer still gets later events, and the new `RunRecord::observer_panics()` counts the caught panics (a record serialized without the field reads as 0), instead of the panic unwinding `execute`/`resume`, losing the record and dropping every running step.
- New `serde` feature: `RunRecord`, `StepRecord`, `ExecutionError`, the ids and the fingerprint serialize.
- New `ExecutionError::Interrupted` (attempt dropped after cancellation; ambiguous) and `ExecutionError::Panicked`. `ExecutionError` is now `Clone` and `PartialEq`, and `ExecutionError::replay_class()` and `ReplayClass` are public.
- New divan bench `scheduler`: plan validation and sequential and parallel execution of 500 no-op steps.
- One replay rule decides both whether `CircuitBreaker::call` re-invokes a step and whether the returned error says replay is safe. A timeout (the breaker's own, or one the step returns, also when wrapped in `StepFailed`) and HTTP 502 or 504 are ambiguous: the attempt may have committed. The breaker re-invokes the step after one only if the step opts in with the new `Step::is_idempotent()` (default `false`), or `FnStep::idempotent()` for closures. HTTP 429 and 503 mean "not processed" and are still retried for every step, so a step that may have committed must not report them. Circuit-open and cancellation never ran the step. Other errors are unchanged.
- **Breaking:** for a non-idempotent step, an ambiguous outcome now comes back as the new `ExecutionError::AmbiguousOutcome { source }` instead of a bare `Timeout` or `Http { status: 502 | 504 }`. That includes the `source` of the `StepFailed` that `execute_pipeline` and `execute_pipeline_parallel` return. `is_retryable()` is `false` for it. Its `DomainError` keeps the inner code, is not retryable, has no `retry_after`, and carries a hint telling the agent to verify whether the operation completed. An idempotent step's ambiguous outcome is still returned bare and stays retryable.
- The `StepFailed` to `DomainError` conversion now keeps the inner error's hints and recovery hint. Before, it rebuilt the error and dropped them.
- **Breaking:** `execute_pipeline` rejects duplicate step ids with `DuplicateStepId` before running anything, the same as `execute_pipeline_parallel`. Before, it ran them.
- **Breaking:** `execute_pipeline` resets every step to `Pending` at the start of a run. When a step fails, every later step is now marked `Skipped` instead of being left alone. Before, statuses from an earlier run survived: re-running a pipeline that started `[Completed, Completed]` with a failing first step left `[Failed, Completed]`, and the second step never ran.
- `execute_pipeline_parallel` rejects duplicate step ids with `DuplicateStepId` before running anything, including ids no edge mentions.
- Cycle detection is iterative, so very large graphs (100,000 steps) no longer overflow the stack.
- `CircuitBreaker` keeps phase, probe and failure count in one state machine. An outcome from a call admitted before the breaker last changed state is ignored: it can no longer reopen a recovered breaker, extend the open window or reset the failure count.
- Depends on `michi-core` (exact version) instead of `michi-core` and `michi-resilience`; versions in lockstep with it.
